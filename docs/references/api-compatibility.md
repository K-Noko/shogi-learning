# APIの後方互換性: 一般的な対処の調べもの

設計書（`docs/design/api.md`）の「レスポンスへのフィールド追加と後方互換性」を決める過程で調べた、一般的な開発での対処をまとめる。このプロジェクトでの決定は設計書に書き、ここには判断の材料だけを置く。出典は2026-09-25に確認した。

## 何が問題になるか

サーバーとクライアントの版がずれて並走すること（version skew）。ローカルの開発ではサーバーとクライアントを同時に変えるので見えにくいが、次の場面で起こる。

- Webアプリ: デプロイ後も、開いたままのタブでは古いJavaScriptが動き続ける
- 配布するクライアント（モバイル・Unity等）: 更新するかどうかはユーザー次第なので、古い版が長く残る

## 対処の4つの層

実際の開発では、これらを組み合わせる。

### 1. 変更の種類を決めておく

「足すのはよい、消す・変える・意味を変えるのはだめ」という規則を明文化し、受け取る側は知らないものを無視する。

- **Tolerant Reader**（Martin Fowler、2011年）: 受け取る側は必要な要素だけを取り出し、知らないものは無視する。これにより、提供側はフィールドの追加等で既存のクライアントを壊さずにインターフェースを変えられる
- **GoogleのAIP-180**: 互換性のある変更とない変更を一覧にしている。例えば、既存のリクエストやリソースに必須のフィールドを足してはならない。クライアントが値を入れるフィールドは、そのフィールドがなかったときと同じ振る舞いを既定にしなければならない。enumの値は、リクエストでしか使わないenumには自由に足してよい。一方、レスポンスで使うenumに新しい値が来うる場合は、そのことを文書に書くべきとしている（利用者のコードが新しい値をうまく扱えない可能性があるため）
- **Protocol Buffers（proto3）**: enumは「open」で、知らない値を受け取ってもフィールドにそのまま保持する。closedなenumが引き起こす予期しない振る舞いを避けるための設計
- Zodでも、知らないenumの値を受け皿の値に落とす書き方をすれば、値の種類の追加を互換性のある変更として扱える

Zodでのオブジェクトの知らないキーの扱いは3通りある。

| 書き方 | 知らないキー |
|---|---|
| `z.object`（既定） | 捨てる（strip）。検証していないデータはアプリのコードに届かない |
| `z.strictObject` | エラーにする |
| `z.looseObject` | そのまま通す |

### 2. バージョンを分ける

壊す変更をせざるを得ないとき、古い形と新しい形を並べて提供し、後で古い方を廃止する。

- URLにバージョンを入れる（`/v1/...`、`/v2/...`）。最も一般的な形
- **GitHub**: `X-GitHub-Api-Version`ヘッダーで日付のバージョン（例: `2026-03-10`）を指定する。指定しなければ`2022-11-28`になる
- **Stripe**: `Stripe-Version`ヘッダーで指定し、指定しなければアカウントの既定のバージョンになる。互換性のない変更を含むのはメジャーリリースだけで、月次のリリースは互換性のある変更だけを含む

### 3. 契約をCIで検査する

互換性を人の注意ではなく機械で守る。

- **スキーマの差分の検査**: OpenAPIの定義を前の版と比べ、壊す変更を検出する（`oasdiff`等。GitHub Actionがある）。FastAPIはOpenAPIの定義を自動で生成するので、このプロジェクトでは導入しやすい
- **消費者駆動の契約テスト**（Pact等）: クライアント側のテストの実行中に「実際に使っている通信の形」を契約として書き出し、サーバー側がそれを満たすかを検査する。クライアントが複数あるときに効く

### 4. 古いクライアントを残さない

- Webアプリ: クライアントが自分の版を送り、ずれていたら再読み込みさせる。**VercelのSkew Protection**は、リクエストにデプロイのIDを付け、古いクライアントのリクエストを古いデプロイへ振り分ける（version locking）。ページ全体の再読み込みでは最新の版を返し、版のずれを検知したクライアントは再読み込みする
- 配布するクライアント: 「最低限サポートする版」を決め、それより古いクライアントには更新を強制する

## このプロジェクトに当てはめると

| 時期 | 状況 | 関係する層 |
|---|---|---|
| Phase1〜3 | クライアントは手元のWebだけで、デプロイもしない。サーバーとクライアントは常に同時に変わる | 1だけで足りる |
| Phase4（デプロイ） | 開いたままのタブの古いJavaScriptが、新しいサーバーと並走する | 4（Web向け） |
| Phase5（Unity） | 本当に並走するクライアントが生まれる | 2・3・4（強制更新） |

- 3のOpenAPIの差分検査は、CIに1ステップ足すだけで試せるので、前倒しの候補になる
- OpenAPIからZodのスキーマを自動生成するかどうかは、CLAUDE.mdの「型を共有して境界をなくす構成は採らない」に触れうるので、導入するときに改めて決める
