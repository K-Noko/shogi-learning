# 設計書: フロントエンド

Walking Skeleton（Phase1）の時点で決まっていることだけを書く。設計書の読み方は[`overview.md`](overview.md)を参照。外した案・経緯・長い論証は[`rationale/frontend.md`](rationale/frontend.md)に、同じ見出しで置く。

フロントエンドは、サーバーが配信する状態を描画し、ユーザーの意図を送るだけの薄いクライアントに徹する（[`overview.md`](overview.md)「全体のアーキテクチャ」）。

## 技術

| 用途 | 技術 |
|---|---|
| UIの土台・ビルド | React＋Vite |
| ルーティング | React Router（フレームワークのモードは使わない） |
| 盤の描画 | Pixi.js |
| 境界の検証 | Zod（Phase3まではレスポンスのスキーマを`z.strictObject`にする。[`api.md`](api.md)「レスポンスへのフィールド追加と後方互換性」） |

- 盤以外のUI（ボタン等）はReactで作り、Reactの画面の中にPixi.jsの描画面を置く
- React Routerは、ルーティングのライブラリとして使うモード（Declarative・Data）に限る。サーバーでの描画を含むフレームワークのモードは、FastAPIとは別の2つ目のサーバーを生むので使わない
- **React RouterはDeclarativeモードで使う**。データの取得と失敗の振り分けはAPIの呼び出しのラッパーが持つので、Dataモードの`loader`・`errorElement`は使わない。使うと、その仕事の一部がReact Routerに固有の仕組みに載り、作り替えで書き直す側が増える
- 状態管理は、初期盤面の段階ではReactの標準の仕組み（`useState`等）で足りる。ルートのコンポーネントが、ラッパーの結果を持つだけのため

外した案: [`rationale/frontend.md`](rationale/frontend.md)「技術」

## 画面のURL

- APIは同じオリジンの`/api/...`を呼ぶ（Viteのプロキシがバックエンドへ転送する。[`api.md`](api.md)「パスの接頭辞とフロントエンドからの接続」）
- 対局の画面のURLに対局IDを入れる（例: `/games/{id}`）。再読み込みしたら、そのIDで`GET /api/games/{id}`を呼んで同じ対局に戻る（[`api.md`](api.md)「Phase1のエンドポイント」）
- 対局の状態は対局IDに紐づけ、IDが変わったら作り直す（Reactなら`key={gameId}`等。[`api.md`](api.md)「新規対局とリセット」）

## フレームワークに依存させない部分

- **Pixi.jsの描画のコードをReactに依存させない**。Reactは描画面を載せ、状態を渡すだけにする。依存を内側（フレームワークに依存しない部分）へ向ける、という規則をフロントエンドに当てはめたもの。後でUIの土台を別のフレームワーク（Svelte等）に作り替えるとき、盤の描画をそのまま持っていけるようにするため
- **APIの呼び出しは、すべて1つのラッパーを通す**。呼び出し先の基点（オリジン。今は同じオリジン）の付加と、レスポンスの検証（Zod）を、ラッパーの1か所で行えるようにするため。別のオリジンを使うことになっても、ラッパーの基点を変えるだけで済む。ラッパーの外で`fetch`を使わないことは、ESLintの規則で守る（`no-restricted-globals`等。ラッパーの中だけ許可する）
- **APIの呼び出しを2段に分け、どちらもReactに依存しないモジュールにする**。Reactのカスタムフックにはしない（フックはReactに依存する）
  - **共通のラッパー**: `fetch`と基点の付加、渡されたZodのスキーマでのパース、結果の振り分けを持つ。どのAPIの呼び出しにも使う。結果は、成功・形式の不正・200以外のステータス（ステータスコード付き）・通信失敗の4種類
  - **APIごとの関数**（例: 対局を取得する関数）: パス（`/api/games/{id}`）の組み立て、そのAPIのZodのスキーマ、描画用の形への変換を持ち、共通のラッパーを通して呼ぶ。Zodの出力（APIの契約の形）を描画層に直接渡さないのは、描画層をAPIの契約に依存させないため。中身が今は同じでも偶然の一致として扱う、バックエンドのAPIの型とドメインの型の分け方と同じ規則（[`api.md`](api.md)「API用の型と変換」）
- **ルーティングの定義は薄く保つ**。ルートのコンポーネントは、URLから対局IDを取り出して対局を取得する関数に渡し、結果の種類に応じて画面に出すもの（成功なら描画層、失敗なら文字列）を決めるだけにする。失敗の表示は「盤以外のUI」なのでReactの側に置く
- **描画を「配置の計算」と「Pixi.jsへの反映」に分ける**。配置の計算は、描画用のオブジェクトから「画面上のマス・文字・回転」の一覧を返す純粋な関数で、向き・文字・回転の判断をすべて持つ。Pixi.jsへの反映は、その一覧をピクセルの位置に換算して置くだけで、判断を持たない。`<canvas>`に描かれた結果はテストで確かめにくいので、判断をテストしやすい側に寄せ、反映は目視で確かめる
- APIの呼び出し（共通のラッパーとAPIごとの関数）と描画のコードからReact・React Routerを`import`しないことは、ESLintの規則（`no-restricted-imports`）で守る

詳しい理由（作り替えのときに何が持っていけるか）: [`rationale/frontend.md`](rationale/frontend.md)「フレームワークに依存させない部分」

## 盤の描画

- **見る人は、当面は先手（black）に固定する**。盤は先手から見た向き（9一が左上。ワールド座標のまま）で描き、後手の駒を180度回転して描く。見る人を選べるようになったら（後手から見た向きへの反転。カメラ座標への変換）、配置の計算の中で変換する。見る人が後手なら、盤全体が反転し、180度になるのは先手の駒の側になる
  - 先手への固定は配置の計算の中だけに閉じる。APIとドメインは見る人に依存しない（盤面はワールド座標のまま返す。[`api.md`](api.md)「盤面のレスポンス」）ので、[`overview.md`](overview.md)「後のPhaseのために今から守る前提」の「後手を選べるようになる前提で設計する」とは食い違わない
- 駒の表記はクライアントが種類・持ち主から決める（[`api.md`](api.md)「盤面のレスポンス」）。最初は漢字一文字で描き、駒の画像化で画像に置き換える。後手の玉将を「玉」と呼び分けるのも、画像化のときに入れる
