# ドメインモデル: 外した案・経緯

[`../domain.md`](../domain.md)の決定について、検討して外した案・経緯・長い論証を、本体と同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

## 座標

- 座標を区別する2つの軸: 「どこから見た座標か」（参照系。先手から見た固定の向きか、見る人によって変わる向きか）と、「位置をどう書き表すか」（表記。筋・段か、左上が原点の`(x, y)`か）は別の軸である。筋・段も`(x, y)`も、参照系の軸ではどちらも先手から見た固定の向きになる。1つの言葉で2つの軸を兼ねると文脈が読み取れなくなるので、4つの座標に名前を分けた。ある言葉の対になる言葉が場所によって違う（「ワールド座標」の対が「筋・段」だったり「カメラ座標」だったりする）のは、軸が2つ混ざっている兆候である
- 「カメラが従」の根拠: 移動のパターンは駒の持ち主から見て定義される（ローカル座標）。後手の駒の180度回転は、ローカル座標からワールド座標への変換であって、見る人の都合（カメラ）ではない。ワールド座標を真として移動のベクトルを回転させるのが、意味として正しい
- 「棋譜が従」の根拠: 筋の「右の方が数字が若い」という尺度を、言語の記述に近い表記の層ではなく低い層に持ち込むと、符号の取り違えが起きやすい
- **筋・段を真として持ち、配列の読み書きなど必要なときだけ`(x, y)`へ変換する**: 棋譜やUSIの着手の表記との変換は素直になるが、上の「棋譜が従」の根拠に反する。変換が処理のあちこちに散る
- **筋・段のまま移動を計算する**: 前進は「段を1減らす」でそのまま書け、左右は筋とxで向きが逆だが、将棋の駒の動きはすべて左右対称なので移動先の集合は変わらない、という理屈で成り立つように見える。しかしこれは、正しさが偶然の性質（左右対称）に支えられているということで、非対称な動きの駒・変則ルール・画面の感覚で書いた移動パターン等で、エラーも出ずに静かに間違える。低い層ほど偶然に頼らない一様な規則で動くべきなので、採らなかった

## 盤と駒

- **駒オブジェクトの配列で盤を持つ**（全枚数が固定である性質を構造で保証する形）: マスから駒を引く処理が回りくどくなる。また千日手の判定で「2枚の歩が入れ替わっただけの局面」を同じ局面と扱うには、駒の区別がかえって邪魔になるため、採らなかった

## 移動のパターン

- 桂馬を特別扱いするフラグを持たない理由: 1マス動くときは移動先だけを確かめ、何マスでも動けるときは途中のマスを1つずつ確かめる、という規則で、桂馬が途中の駒を飛び越えられることが自然に成り立つ

## 着手

- **Phase1で成り・打つの形を持たない理由の詳細**: APIの契約でも同じ理由で留保した（[`../api.md`](../api.md)「着手の形」）。APIの型とドメインの型は独立なので、APIで留保したこと自体はドメインで留保する理由にならない。しかし、変えにくいAPIの契約でさえ留保したものを、テストがあれば自由に直せるドメインの型で前借りする理由はない（変えやすいものほど遅く決めてよい。`docs/references/design-principles.md`「いつ決めるか」）
- 「右」「直」等を着手に持たせない理由: 着手とその直前の局面から計算で出せるうえ、棋譜の形式によって要るかどうかが違う（CSA形式やUSIは移動元のマスを直接書くので使わない）

## 着手と指した結果を分ける

- **1つの型にまとめる**: Moverが返す段階では結果がまだ計算されていないため、結果のフィールドは空（`None`）を許すしかない。すると、取った駒が`None`のとき「何も取らなかった」のか「まだ計算していない」のか区別できず、型チェッカーも「履歴の手なら必ず埋まっている」ことを知らない。またMoverが結果に値を入れて返しても型の上では止められない

## 用語

- **`sente`・`gote`**: 英語圏の将棋コミュニティでも通じるが、駒の名前を英語にするなら揃わない
- **ローマ字の駒名**（CSA形式の`FU`・`KY`等の文化）: エンティティの名前にマルチバイト文字を使わない方針から日本語は外し、ローマ字よりはUSIの英語を採った
