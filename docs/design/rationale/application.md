# アプリケーション層: 外した案・経緯

[`../application.md`](../application.md)の決定について、検討して外した案・経緯・長い論証を、本体と同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

## 位置づけ

- **GameSessionとMoverをドメインに置く**: GameSessionの仕事には、性質の違う2種類が混ざっている。盤面・手番・履歴を持ち、着手を適用して結果を作るのはゲームのルールそのもので、同期的で外の世界を知らない。一方、手番のMoverに次の手を問い合わせて待つのは、外の世界とのやり取り（人間はHTTP越し、Botは乱数、Phase2のエンジンは別プロセス）で、非同期の待ちを含む。前者をドメインの対局に、後者をアプリケーション層のGameSessionに分けた。ドメインの対局は非同期もI/Oもない普通のクラスになり、そのままテストできる
- この分け方は、ドメイン駆動設計（Evans）の「ルールと状態を持つエンティティをドメインに置き、それを使って手順を進めるアプリケーションサービスを外側に置く」形と、ヘキサゴナルアーキテクチャ（Cockburn）の「出入り口（ポート）と、そこに差し込む実装（アダプター）」の形にあたる
- 見分けるための問い: クラスの仕事の中に「待つ」「外から来る」が出てきたら、それはルールではなく、外とのやり取り（アプリケーション層）の仕事である

## APIの層との境目

- **APIの層が、入れ物の中身をたどってドメインの盤を取り出す**（例: `registry[game_id].board`）: アプリケーション層の中身が変わると、APIの層まで書き換えが波及する（入れ物の中身がGameSessionになると`registry[game_id].game.board`に変わる）。層の境目を中身の構造で決めている状態で、オブジェクトの中身をたどって遠くまで手を伸ばさないという経験則（デメテルの法則）にも反する。境目を操作で決めた（Fowlerの「サービス層」、クリーンアーキテクチャの「ユースケース」と同じ考え方）
- 「後から中身を作ると経路の手戻りが出るので、作り直しを後のタスクに明記する」という考え方は、境目の操作を今の時点で決めきれないときに正しい。その場合は手戻りを隠さず`debt`として記録する。今回は、必要な操作（作る、引く、着手を受け付ける）が見えているので、境目を今決められた
- 見分けるための問い: ある変更が別の層にまで波及しそうに見えたら、境目の決め方を疑う

## GameSession

- **初期盤面を表示するだけの段階で、中身が対局だけのGameSession（殻）を作る**: Moverも`run()`ループもない殻になる。殻を作っても、Moverや`run()`の形を推測で決める必要は生まれない（それらは殻の有無にかかわらず、着手を扱うIssueで決まる）。殻の利点は「APIの層が盤を取り出す経路が、着手を扱うIssueで変わらない」ことだけだったが、境目を操作で決めれば（上記「APIの層との境目」）その利点は操作の境目が担うので、殻は要らない。依存の階層（APIの層→アプリケーション層→ドメイン）も、入れ物がアプリケーション層にあるので殻なしで成り立つ。GameSessionは、存在理由（Moverとやり取りして対局を進める）が生まれるときに作る
- **初期盤面の段階で「IDと盤だけ」を持つ仮の型を作り、後でGameSessionに置き換える**: 仮の型は捨てることになる。ドメインの対局を最初から作り、入れ物はそれを保持すれば、捨てる型がない
- 経緯: GameSessionをドメインに置いていた構造では、盤を持つのはGameSession自身の仕事だったので、「GameSessionを今作り、中身は盤だけにして育てる」が成り立っていた。層を分けて盤を対局（ドメイン）の仕事にしたことで、その前提が消えた

## 対局の入れ物

- **ドメインに置く**: 対局の保持と検索は、ゲームのルールではない
- **APIの層のルーターと同じファイルに置く**: HTTPの受け答えと対局の保持は、変わる理由が違う（関心の分離）。ルーターとはファイルを分け、アプリケーション層として扱う
