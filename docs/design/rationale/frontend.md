# フロントエンド: 外した案・経緯

[`../frontend.md`](../frontend.md)の決定について、検討して外した案・経緯・長い論証を、本体と同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

## 技術

- **Next.js**: ルーティングのためだけに使うには、抱え込むものが多すぎる
  - Next.jsの価値の中心は、サーバーでの描画・React Server Components・Server Actions等のサーバー側の機能にある。このプロジェクトはサーバーの役割をすべてFastAPIに置くので、その価値を使わない
  - 使うと、Node.jsの2つ目のサーバーがFastAPIとクライアントの間に入り、「真実の源はバックエンド」の「バックエンド」が2つになる。サーバーを持たない静的なサイトとして書き出すモード（static export）もあるが、`generateStaticParams()`なしの動的なルートに対応しないので、`/games/{id}`のようにIDが実行時に決まるURLと相性が悪い
  - 使わない機能も、攻撃される面としては抱え込む。実例として、2025年12月にReact Server Componentsの脆弱性（CVE-2025-55182、通称React2Shell。CVSS 10.0。認証なしでサーバー上の任意のコードを実行できる）が公表され、公表から数時間で実際の攻撃に使われた。Next.jsも影響を受けた（CVE-2025-66478として追跡）
- **React Routerのフレームワークのモード**: サーバーでの描画を含むので、Next.jsと同じ理由で使わない
- **React RouterのDataモード**: ルートの`loader`で画面を描く前にデータを取得し、`errorElement`で失敗を表示できる。`loader`の中でラッパーを呼ぶだけにすればルートは薄く保てるが、失敗の扱いを`errorElement`等に載せると、ラッパーの結果の振り分けと役割が重なり、作り替えで書き直す側も増える。Declarativeモードでは`useEffect`で取得して結果をReactの状態に持つ処理を自分で書くが、対局IDが変わったときに古い結果が後から届く問題は、`key={gameId}`で画面ごと作り直すことで避けられる
- **TanStack Router**: URLの引数まで型で扱えるのが特長の、React Routerの代わりになるルーティングのライブラリ。検討の対象には入るが、今回はより標準的なReact Routerを採った
- **`@pixi/react`**: Pixi.jsの描画をReactのコンポーネントとして書くライブラリ。描画のコードがReactに依存するので、「Pixi.jsの描画のコードをReactに依存させない」（[`../frontend.md`](../frontend.md)「フレームワークに依存させない部分」）と食い違う
- **Svelte**: 今は選ばない。ポートフォリオとして今のフェーズで作りこみたい箇所はバックエンド・テストエンジニアリングに大きく寄っている。作り替えたくなるのはフロントエンドの性能を作り込むとき。作り替えを安くするための構造は「フレームワークに依存させない部分」で先に取っておく
  - Svelteに作り替える場合も、SvelteKitは同じくサーバーでの描画を含むフレームワークなので、Next.jsを外したのと同じ問いがもう一度立つ（SvelteKitはサーバーでの描画を切ってSPAとして動かすモードを持つ）

## フレームワークに依存させない部分

### APIの呼び出しのラッパー

- 呼び出し先の決め方の温度感を、次の2つから選ばずに、ラッパーの規則に置き換えた
  - **「CORSを採らなかったので、バックエンドのURLを書く必要がないだけ」（規則にしない）**: コンポーネントの中に`fetch`が散らばりうる。検証や基点の付加を足すときに、散らばった呼び出しをすべて直すことになる
  - **「絶対のURLで書いてはいけない」（相対パスを絶対の規則にする）**: 別のオリジンを使う道を、コードの側で閉じてしまう
  - 本当に守りたいのは「`fetch`が乱立しない（呼び出しが1つのラッパーを通る）」ことだった。基点はラッパーの1か所で決まるので、別のオリジンの道も閉じない
- 相対パスであることをテストで確かめない理由: コンポーネントに`http://localhost:8000`を直接書くと、開発中のブラウザからは別のオリジン（`5173`から`8000`）への呼び出しになり、CORSのエラーですぐに壊れる。ずれが静かではなくうるさく起きるので、テストで守る価値が小さい。守る価値があるのはラッパーを通ることの方で、これはテストよりリンターの規則に向く

### 作り替えのときに、何を持っていけるか

| 資産 | Svelteに作り替える場合 | Unityクライアントを作る場合 |
|---|---|---|
| APIの契約（サーバー側） | そのまま | そのまま。Unityクライアントを足せることが、「真実の源はバックエンド」「薄いクライアント」を選んだ理由 |
| Pixi.jsの描画のコード | Reactに依存させていなければ、そのまま持っていける | 持っていけない（言語がC#） |
| APIの呼び出し・Zodのスキーマ | Reactに依存させていなければ、そのまま持っていける | 持っていけない。ただしFastAPIが生成するOpenAPIの定義から、C#の型を生成する道がある |
| ルーティングのコード | 書き直し（SvelteKitはファイルの置き場所でルートを決める方式で、書き方がまったく違う） | 書き直し。そもそもUnityにはURLのルーティングがなく、シーンの切り替えになる |
| ルーティングの設計（どのURLで何を表すか） | そのまま（`/games/{id}`という形は、ブックマーク等で利用者が依存する約束で、ライブラリとは独立している） | 対応する概念（「対局IDで対局の画面を開く」）として持っていける |
| Reactのコンポーネント・状態管理 | 書き直し | 書き直し |

- ルーティングは、コードは移行できず、設計（URLの形）だけが移行できる。なので、ルーティングの定義に処理を載せず、URLから対局IDを取り出して、フレームワークに依存しない部分へ渡すだけにしておくと、書き直す量が最小になる
- Unityクライアントで持っていけるのは、サーバー側とAPIの契約だけ。フロントエンドのコードの構造は、Webの中でのフレームワークの作り替えにしか効かない

### ラッパーとルートの分担

- **Zodのスキーマとバリデーションを、ルートのコード（React Router）に持たせる**: 上の表のとおり、ルーティングのコードは作り替えで書き直しになるので、スキーマとバリデーションも一緒に書き直すことになる。Pixi.jsの描画をReactに依存させない理由（作り替えで持っていける）と逆の結果になる
- **ラッパーをReactのカスタムフック（`useGame`等）にする**: 「ラッパーを経由して呼ぶ」形にはなるが、フックはReactに依存するので、作り替えで持っていけない
- **ルートがAPIのパス（`/api/games/{id}`）を組み立ててラッパーに渡す**: APIのパスの形は、Zodのスキーマと同じくAPIの契約についての知識。APIごとの関数に置けば契約の知識が1か所にまとまり、書き直す側のルートが持つ知識も減る
- **対局を取得する関数が、自分で`fetch`する（共通のラッパーを1段にまとめない）**: 「APIの呼び出しは、すべて1つのラッパーを通す」（`fetch`の乱立を防ぎ、基点の付加と検証を1か所にする）と食い違う。`fetch`・基点・パース・結果の振り分けはどのAPIでも同じなので共通のラッパーに置き、APIごとに違うもの（パス・スキーマ・変換）だけをAPIごとの関数に置く

### 描画を「配置の計算」と「Pixi.jsへの反映」に分ける

- 描画の結果を確かめる他の手として、Pixi.jsの表示物（シーングラフ）を調べる手と、画面を撮って前回と比べる手（ビジュアルリグレッション）がある。前者はテストの環境でPixi.jsを動かす準備が要り、後者はブラウザを動かす仕組みが要る。どちらも初期盤面の段階では手間に見合わない
- 判断を持たない薄い殻（Pixi.jsへの反映）と、判断を持つテストしやすい部分（配置の計算）に分ける形は、ハンブルオブジェクト（Meszaros『xUnit Test Patterns』）と呼ばれる
- 配置の計算が返す位置は、ピクセルではなく画面上のマス（何列目・何行目）にした。マスの大きさは表示の都合で変わりやすく、テストに持ち込むと大きさを変えただけで落ちるため。後手の視点（カメラ座標への変換）を入れるときは、この計算の中で変換する
