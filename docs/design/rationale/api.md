# API契約: 外した案・経緯

[`../api.md`](../api.md)の決定について、検討して外した案・経緯・長い論証を、本体と同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

## 対局の作成とURL

- **IDを持たない`/game`**: 「サーバーに対局は1つしかない」という前提が、実装ではなくAPI契約に入る。リクエストで対局を指定できないため、ブラウザのタブを2つ開くだけで同じ対局を操作して混線する。内部の暫定実装ならサーバーの中だけで直せるが、契約はクライアントが依存する面なので、直すには全クライアントを同時に変える必要があり、清算できる負債にならない。また、対局がいつ・誰の操作で生まれるかがAPIに現れず、生成とリセットの区別が溶ける
- **クライアントがIDを振る`PUT /games/{id}`**: 作成が冪等になる（再送しても対局が重複しない）が、IDを振る責務がクライアントに漏れる。これが外した主な理由
  - なお、冪等性そのものも今は必須ではない。再送で重複した対局は、IDがクライアントに届いていないので誰も参照しない孤児になるだけで、混線は起きず、バックエンドが回収すれば済む。ただしこれは、作成に対局そのもの以外の副作用がない間に限る（Phase4の人間同士の対局で、作成が相手への通知等を伴うようになると成り立たない）
  - 冪等性が必要になったときも、POSTのまま`Idempotency-Key`ヘッダーで足せるので、この案に移る理由にはならない

## 新規対局とリセット

- 経緯: 前に作った囲碁のアプリには対局ID（セッションの粒度）がなく、1つのセッションの中でリセットして対局を繰り返していた。対局IDがあれば、「対局をやり直す」は「新しい対局を作る」で表せる
- 新しい対局を作る形にすると持ち越しが起こりにくい理由: 既存のオブジェクトを初期値に戻すリセットは、フィールドが増えるたびに戻し忘れが起こりうる。新しいオブジェクトを作れば、何も持ち越さないのが既定になる
- 古い対局の回収に`DELETE /games/{id}`だけを使わない理由: タブを閉じた場合や、再送で生まれた孤児を回収できない

## 盤面のレスポンス

- **成っているかを今から載せる**: Phase1では常に`false`になるフィールドを契約に載せると、クライアントは次のどちらかになる
  - 「Phase1では成らない」という、契約に書かれていない知識を前提に無視する（知るべきでない情報を前提にした実装）
  - 契約どおりに扱い、成った駒の描き分けを作る（起こりえない世界を表すコード。Phase1では動かして確かめられない）
- SFENをPhase1で出さない理由の詳細: 盤面注入（Phase2）ではクライアントがSFENを送る側で、USIエンジンとのやり取りはサーバーの中で完結する
- **SFENだけを返す**: 全クライアントにSFENのパーサーが要り、Zodで検証できるのが「文字列であること」までになる
- **構造化したマス目とSFENの両方を返す**: Phase1では使う側がない。後からフィールドを足すコストも小さい（Phase3まではクライアントを同時に追従させ、Phase4以降はフィールドの追加が後方互換になる）ので、先に入れる理由がない

## Phase1のエンドポイント

- ルーティングを最初から入れる理由: Walking Skeletonの要件には再読み込みからの復帰はないが、開発中は再読み込みが多く、ルーティングはフロントエンドの構成の決定なので後から入れるより手戻りが小さい。対局をURLで指し示せるものにする考え方（「対局の作成とURL」）とも揃う
- **対局IDを`localStorage`に置く**: 同じブラウザのタブは`localStorage`を共有するので、タブを2つ開くと同じ対局を取り合う。IDのない`/game`を外したのと同じ混線が、画面の側で起きる
- **`GET`を作らない**（再読み込みしたら新規対局）: 最も簡単だが、上の理由でルーティングを最初から入れることにした

## API用の型と変換

- この規則は、「外部からの入力をどのMoverに届けるかを判定するのは、APIの層だけ」（[`../overview.md`](../overview.md)「内部の仕組みとクライアントへの届け方を分ける」）と同じ規則を、型に当てはめたもの。外の都合をドメインに持ち込まない（依存性のルール。`docs/references/design-principles.md`「層と依存の向き」）
- 変換の層が要ることは、Phase1の時点ですでに決まっていた。状態のレスポンスは盤面・手番・直前の着手・合法手の一覧を組み立てたもので、ドメインのどのオブジェクトとも一致しない。盤面のレスポンスは持ち駒を含めず、並び順もクライアントの都合で決めた
- 着手の型も分ける理由: Phase3で手数による確認（「エラー」）を入れると、リクエストは「着手＋手数」になるが、手数は通信の都合の情報で、棋譜の1手には要らない。ドメインの着手の型をそのまま使っていると、手数が棋譜の1手に混ざる
- **ドメインやDBのモデルをそのままレスポンスに使う**: 小さなFastAPIのアプリではよく見られる形で、層を分ける手間を省くための割り切り。このプロジェクトは採らない

## 着手の形

- **座標を筋・段のオブジェクト（`{"file": 7, "rank": 7}`）で表す**: JSONを人間が見たときに棋譜の表記と対応がすぐわかる利点はあるが、ドメインの位置の真はワールド座標で（[`../domain.md`](../domain.md)「座標」）、盤面のレスポンスもワールド座標の順の配列である。着手と合法手が筋・段だと、クライアントは「このマスの駒を持ち上げられるか」を調べるたびに配列の添字と筋・段を変換する必要があり、筋の「右の方が数字が若い」尺度がフロントエンドに漏れる。人間向けの表記はサーバーが返せば済む
- **座標をUSIの文字列（`"7g"`）で表す**: パースが要り、Phase1ではUSIをバックエンドの外に出さない方針とも合わない
- **`type`と`promote`を今から持たせる**
  - 変更の種類が違う。成りは同じ型にフィールドを足す変更で、既存の読む側は影響を受けない。打つは型に種類を足す変更で、打つ手には移動元がないので、移動元を読んでいたすべての場所（合法手の絞り込み、直前の手の強調、変換等）が「移動か」を確かめる必要に迫られる
  - それでも`type`を先に持つ理由にはならない。読む側への波及の原因は`type`がないことではなく、移動元を持たない種類が現れることなので、Phase1から`type: "move"`を持っていても波及は避けられない。先に持って節約できるのは、JSONのキーとスキーマの包み直しだけ
  - 今から持たせる側だけが、Phase1に新しい判断を生む。Phase2の設計の前に推測した形を契約として固定することにもなる。後から足すなら、その判断はPhase2で、そのとき持っている情報で行える。Phase3まではクライアントを同時に追従させるので、後から足すコストは1回の同時修正で済む
  - 「確実にロードマップにあり、対局の成立に要るものは今から持つ」という基準は採らない。確実に要ることはYAGNIの例外にならない（`docs/references/design-principles.md`「いつ決めるか」）うえ、この基準ではWalking Skeletonのための簡略化（持ち駒を返さない、駒取りがない等）がすべて棄却されてしまう
- リクエストの知らないフィールドを弾く理由の詳細: クライアントのレスポンスの検証をstrictにしたのと対称。Phase4以降も、サーバーを先にデプロイすれば「新しいクライアントが古いサーバーに送る」組み合わせは起きないので、弾く形のままでも困りにくい

## エラー

- ステータスコードを分ける意味は、クライアントがコードを見て取るべき行動を変えられることにある。`409`（状態との衝突）なら状態を取り直せば回復でき、`422`（中身の問題）なら取り直しても直らない
- 合法手の一覧を返すので、正規のクライアントが指せない手を送るのは、状態が古いか、クライアントのバグかのどちらかになる。前者は本来`409`にしたいが、区別できないまま使い分けてもクライアントの行動を正しく変えられない
- 手数による確認は、HTTPの`ETag`・`If-Match`で行う方式もある。合法手の判定では防げない種類のバグ（古いタブの手が進んだ局面でたまたま合法）を防ぐ点で、ステータスコードの区別以上の意味がある
- Phase3の最後に入れる理由: Phase1〜3で同時の操作が起きるのは、同じ対局のURLを2つのタブで開いたときだけ。リクエストに必須のフィールドを足すことになるが、Phase3まではクライアントを同時に追従させるので問題にならない

## 駒の選択と合法手

- 選択をサーバーの状態にすると、選択がタブ間で共有されて混線する
- Phase2では、成りの選択（「成りますか」を聞くかどうか）を、一覧に成る手と成らない手の両方があるかどうかで決められる。打つ手も同じ一覧に入る
- **合法手を届けない**（送ってみて弾かれたら指せない手）: 相手の駒も持ち上げられてしまう。防ぐにはフロントエンドで「自分の駒か」を判定するしかなく、ルールが漏れる
- **持ち上げるたびに問い合わせる**（例: `GET /games/{id}/legal-moves?from=7g`）: サーバーの状態は変えないが、問い合わせるまで持ち上げられるかどうかがわからない。「持ち上げようとしてから、できないと知る」構造は、合法手を届けない案と変わらない。クリックのたびに通信の往復も入る

## クライアントに置く変換の線引き

- **「ルールは漏らさない、描画の変換は漏れてもよい」の2分類だけで線を引く**: 表記の約束（筋・段との対応、SFEN等）はルールではないので、この2分類では判定できない。しかし正解がドメインで1つに決まる知識なので、クライアントごとに実装するとずれる危険がある。SFENへの変換をクライアントに持たせない（「盤面のレスポンス」）のは、この理由による
- 駒の漢字の表記をクライアントに置いてよい理由: 8種類×持ち主×成りの小さく閉じた対応表で済み、将棋のルールが変わっても変わらないので、ずれる余地がほとんどない

## レスポンスへのフィールド追加と後方互換性

- この後方互換性は、RESTやHTTPのプロトコルが保証するものではなく、クライアントのパースの方針で成り立つ規約である
- stripは知らないキーを通すのではなく捨てるので、Tolerant Readerに切り替えても、検証していないデータがアプリのコードに届くことはない
- 値の種類の追加の例: 直前の着手に「打つ」が加わると、「移動」しか知らないクライアントは読めない
- strictをやめることで失うのは、「サーバーがクライアントの知らないものを送ってきた」ことの検知である（任意のフィールドの綴り間違い、意味を変える追加）
- 並走する古いクライアントの例: 開いたままのタブの古いJavaScript、更新されていないUnityクライアント
