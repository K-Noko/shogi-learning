# 設計書: 全体像

全体像は粗く、Walking Skeleton（Phase1）に必要な部分だけを詳しく書く。細部は各Issueの下書きの段階で詰める。

## 設計書の読み方

設計書は領域ごとのファイルに分かれ、それぞれに決定と、実装中の判断に効く短い理由を書く。検討して外した案・経緯・長い論証は`rationale/`の同じ名前のファイルに、同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

| ファイル | 内容 |
|---|---|
| `overview.md`（このファイル） | 目的とスコープ、全体のアーキテクチャ、全体を貫く設計方針、開発基盤、ロードマップ |
| [`domain.md`](domain.md) | ドメインモデル（対局、座標、盤と駒、移動、合法手の判定、着手、用語） |
| [`application.md`](application.md) | アプリケーション層（GameSession、Mover、対局の入れ物） |
| [`api.md`](api.md) | API契約（Phase1の分） |
| [`frontend.md`](frontend.md) | フロントエンド（技術、画面のURL、フレームワークに依存させない部分） |
| `engine.md` | USIエンジンとの連携。Phase2で作る |

## 目的とスコープ

人間がBotと将棋を指せるWebアプリ。一次目的はWebフルスタック開発技術の体得であり、アプリは副産物（CLAUDE.md参照）。

## 全体のアーキテクチャ

バックエンドは、外側から内側へ入れ子になった3つの層で作る（クリーンアーキテクチャ・ヘキサゴナルアーキテクチャと同じ考え方。依存は外側から内側へだけ向ける）。

```
フロントエンド（React＋Vite。盤の描画はPixi.js、境界の検証はZod）
   │ HTTP・JSON（Phase1はREST。Phase2でSSEを加える）
   ▼
┌─ APIの層（FastAPI） ──────────────────────────────────────────┐
│ ルーター（/api/...）                                          │
│ API用の型（Pydantic）とドメインの型との変換                   │
│ 外からの入力を、どの対局・どのMoverに届けるかの判定           │
│                                                               │
│ ┌─ アプリケーション層 ──────────────────────────────────────┐ │
│ │ 対局の入れ物（IDから対局を引く）                          │ │
│ │ GameSession（run()ループ。手番のMoverに問い合わせて待つ） │ │
│ │ Moverの出入り口と実装（人間用・RandomMover）              │ │
│ │                                                           │ │
│ │ ┌─ ドメイン ───────────────────────────────────────────┐  │ │
│ │ │ 対局（Game）: 盤・手番・履歴、着手の適用と結果の作成 │  │ │
│ │ │ 盤・駒・着手・座標                                   │  │ │
│ │ │ ルールのモジュール（移動の計算・合法手の判定）       │  │ │
│ │ └──────────────────────────────────────────────────────┘  │ │
│ └───────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
  後のPhaseで外側に加わるもの: USIエンジン（Phase2。別プロセスで、Moverの実装の1つとしてつなぐ）、
  PostgreSQL（Phase3）、Unityクライアント（Phase5。同じAPIを使う別のクライアント）
```

- **依存は外側から内側へだけ向く**。内側の層は外側の層を知らない。import-linterの契約（APIの層 → アプリケーション層 → ドメイン）でCIに守らせる
- **ドメイン**は、ゲームのルールと状態だけを持つ。非同期の待ちもI/Oも持たない、普通のクラスと関数で書く。「この局面でこの手を適用すると、この結果になる」を、そのままテストできるようにするため
- **アプリケーション層**は、ドメインを使って対局を進める。外の世界とのやり取り（人間の入力を待つ、Botに問い合わせる、Phase2のエンジンと話す）を含むので、ドメインから分ける。Moverは「次の手をくれる出入り口」で、人間・`RandomMover`・USIエンジンは、その出入り口に差し込む実装にあたる
- **APIの層**は、HTTPの受け答えと、API用の型への変換を持つ

詳しい理由と外した案: [`rationale/overview.md`](rationale/overview.md)「全体のアーキテクチャ」

### 最初のレスポンスの流れ

最初の機能（初期盤面）で、初期盤面が画面に描かれるまで。層の役割分担の例として示す。最初の機能では対局を作る操作（`POST /api/games`）を持たず、サーバーの起動時に`test`という対局をスタブとして仕込み、それを`GET`で引いて描く。対局を作る操作は後の機能で入り、そのときスタブを撤去する。

```
サーバーの起動時
[アプリケーション層] 対局のIDとして "test" を採番する
   │   ├→ [ドメイン] 平手の初期配置の盤を作る
   │   └→ [ドメイン] IDと盤を受け取って対局を作る
   ▼
[アプリケーション層] 対局のIDで入れ物に登録する

対局の画面を開いたとき
[画面] /games/test を開く（React Routerが対局IDを取り出す）
   ▼
[画面] 対局を取得する関数が、共通のラッパーを通して GET /api/games/test を呼ぶ
   ▼
[APIの層] アプリケーション層の「IDで対局を引く」を呼ぶ（見つからなければ例外 → 404）
   ▼
[APIの層] 対局をAPI用の型に変換して返す
   │ 200 { id, board }
   ▼
[画面] 共通のラッパーがZodに通して結果を振り分け、対局を取得する関数が描画用の形に変換して返す
   ▼
[画面] 成功なら、配置を計算してPixi.jsで盤と駒（漢字）を描く。失敗なら、失敗の種類を文字で表示する
```

- **ルールと状態の真実の源は、常にバックエンド**。フロントエンドは、サーバーが配信する状態を描画し、ユーザーの意図を送るだけの薄いクライアントに徹し、ルールのロジックを持たない。将来のUnityクライアントを、同じAPIを使う別のクライアントとして足せるようにするため
- **境界では両側で検証する**。バックエンドはPydantic、フロントエンドはZodで、受け取ったJSONを境界でパースする。型を共有して境界そのものをなくす構成（tRPC等）は採らない
- **APIの契約の持ち主はAPIの層**。ドメインはAPIの層を知らない（[`api.md`](api.md)「API用の型と変換」）
- 本番用のバックエンドのイメージはDockerfileで作る（下記「開発基盤」）
- 各層の詳細は、ドメインは[`domain.md`](domain.md)、アプリケーション層は[`application.md`](application.md)、API契約は[`api.md`](api.md)、フロントエンドは[`frontend.md`](frontend.md)。全体を貫く設計方針は下記「内部の仕組みとクライアントへの届け方を分ける」

## Walking Skeletonの要件

Phase1の最初の到達点。「駒が動いて、取り合いすら起きない序盤だけなら指せる」ことを目指す。

- 平手の初期配置の盤面がある
- 駒は、その駒の動きに沿って、他の駒がいなければ移動できる
  - 飛車・角・香車は、通り道と移動先の両方が空いている必要がある。それ以外の駒は移動先だけ。桂馬は途中の駒を飛び越えられる
  - 移動先に相手の駒がいる場合も移動できない（駒取りはない）
  - 成り・行き所のない駒の判定もない。桂馬が敵陣の奥に入ると動けなくなることがあるが、許容する
- 人間の手番と相手（Bot）の手番を処理できる。相手は`RandomMover`（合法な移動からランダムに選ぶ）
- 新規対局を始められる（リセットの操作は作らない。[`api.md`](api.md)「新規対局とリセット」）
- 終局はない。駒を取れない以上、ゲームの中で終局が起こりえないため。終局がない前提の実装を作らず、終局の仕組みごとPhase2に留保する

## 内部の仕組みとクライアントへの届け方を分ける

- **内部**: アプリケーション層のGameSessionの`run()`ループが、今の手番のMoverの`propose_move()`を待ち、返ってきた着手をドメインの対局に適用する。人間の手もBotの手も同じ形で待つ。**GameSessionとドメインは人間とBotを区別しない**（`if is_human:`のような分岐を入れない）。外部からの入力をどのMoverに届けるかを判定するのは、APIの層だけ
- **クライアントへの届け方**: Phase1では、POSTのレスポンスを、Botが応答して再び人間の手番に戻るまで待たせてから返す（同期）。Phase2の序盤でSSEによる非同期の配信に切り替える。切り替えで変わるのは届け方だけで、内部には手を入れない
- 届け方の問題を内部の分岐で解決すると、後で清算に手こずるため、この2つを最初から分けておく

詳しい経緯: [`rationale/overview.md`](rationale/overview.md)「内部の仕組みとクライアントへの届け方を分ける」

## 開発基盤

Phase1で入れる。

| 用途 | バックエンド | フロントエンド |
|---|---|---|
| 言語・実行環境 | Python 3.14 | Node 22.18.0 |
| パッケージ管理 | uv 0.12.17 | npm |
| リンター・フォーマッター | ruff | ESLint（typescript-eslint）＋Prettier |
| 型チェッカー | pyright | TypeScript |
| テスト | pytest（プロパティベーステストはHypothesis） | Vitest |
| 依存の向きの検査 | import-linter | — |
| 境界の検証 | Pydantic | Zod |

- CIはGitHub Actions。検査はランナー（GitHub Actionsの仮想マシン）で直接回す
- PythonとNodeのバージョンの正は、`.python-version`と`.nvmrc`の1か所に置く。CIも、ワークフローに書かずにこの2つのファイルから読む
- 本番用のバックエンドのイメージはDockerfileで作り、CIでビルドして確かめる
- 道具は、それを使う対象が生まれるIssueで入れる。一覧に載っていても、使う場面のない設定だけを先に作らない（Zod・import-linterは初期盤面、Hypothesisは人間の着手のIssueで入れる）
- import-linterで、依存が外側から内側へだけ向くこと（APIの層 → アプリケーション層 → ドメイン。上記「全体のアーキテクチャ」）をCIで守らせる
- typescript-eslintは、型の情報を使う推奨の規則の一式（`recommendedTypeChecked`）を使う。`no-unsafe-*`で、`any`（`response.json()`の戻り値等）をZodでパースせずに使うことを禁止する
- 型チェッカーはpyright。Pydanticを設計の中心に置くため、Pydanticへの対応の実績を重視した（pyrightはプラグインなしで対応している）
- リンターはESLint＋Prettier。予定の規則（`no-unsafe-*`等）はoxlintでも使えるが、oxlintの最大の長所の速さがこの規模では効かないので、規則とプラグインの広さと、標準であることを取った
- ミューテーションテスト（mutmut）は、検査する対象のテストが揃ってから、独立したIssueで入れる

詳しい理由と外した案: [`rationale/overview.md`](rationale/overview.md)「開発基盤」

## ポート

| 用途 | ポート |
|---|---|
| フロントエンド（Viteの開発サーバー） | `5173` |
| バックエンド（FastAPI） | `8000` |

- **使用中なら別のポートへ逃げずに、起動を失敗させる**。逃げると、どのポートで動いているかを追えなくなるため
  - Vite: `server.port`に加えて`server.strictPort: true`を設定する（`port`だけでは、使用中のとき次の番号へ黙って逃げる）。`vite preview`にも`preview.port`・`preview.strictPort`を設定する
- フロントエンドからバックエンドへは、Viteの開発サーバーのプロキシで接続する（[`api.md`](api.md)「パスの接頭辞とフロントエンドからの接続」）
- 番号は、使う各所（Viteの設定、プロキシの転送先）に直接書き、1か所にはまとめない。ずれても、ブラウザで開いた瞬間につながらずに気付ける（静かにずれるバージョンとは違う）ため

## 画面

Phase1の画面。

- 盤面はPixi.jsで描く。Reactの画面の中にPixi.jsの描画面を置き、盤以外のUI（ボタン等）はReactで作る。盤をReactのDOM（HTML要素）で組んでから後でPixi.jsへ移行すると煩雑なので、最初からPixi.jsにする
- Walking Skeletonの駒は漢字の文字で描く。Phase1の最後で画像に切り替える

フロントエンドの技術と構造は[`frontend.md`](frontend.md)。詳しい経緯: [`rationale/overview.md`](rationale/overview.md)「画面」

## 後のPhaseのために今から守る前提

- **後手を選べるようになる前提で設計する**。盤面の表示の向きや座標の扱いを、人間が先手であることに依存させない
- **「人間は1人だけ」という前提の実装を置かない**。置く場合も、清算できる負債（`debt`のIssueと「暫定実装」の注記付き）にする
- **駒落ち・持将棋は、後から組み込める余地だけを残す**。実装はしない
- **棋譜は内部で構造化して持ち**、将棋の表記の文字列や棋譜ファイル（KIF・CSA等）へ変換できるようにする
- **局面の文字列表現にはSFENを使う**。盤面注入の入力形式にSFENを使えば、棋譜の読み込み・USIエンジンとの受け渡しにも同じ仕組みを使い回せる
