# 設計書: 全体像

全体像は粗く、Walking Skeleton（Phase1）に必要な部分だけを詳しく書く。細部は各Issueの下書きの段階で詰める。

## 設計書の読み方

設計書は領域ごとのファイルに分かれ、それぞれに決定と、実装中の判断に効く短い理由を書く。検討して外した案・経緯・長い論証は`rationale/`の同じ名前のファイルに、同じ見出しで置く。決定の文言だけでは実装が自明に決まらないときに読む。

| ファイル | 内容 |
|---|---|
| `overview.md`（このファイル） | 目的とスコープ、全体のアーキテクチャ、全体を貫く設計方針、開発基盤、ロードマップ |
| [`domain.md`](domain.md) | ドメインモデル（座標、盤と駒、移動、合法手の判定、着手、用語） |
| [`api.md`](api.md) | API契約（Phase1の分） |
| [`frontend.md`](frontend.md) | フロントエンド（技術、画面のURL、フレームワークに依存させない部分） |
| `engine.md` | USIエンジンとの連携。Phase2で作る |

判断の拠り所にした一般的な考え方の調べものは`docs/references/`にある。

## 目的とスコープ

人間がBotと将棋を指せるWebアプリ。一次目的はWebフルスタック開発技術の体得であり、アプリは副産物（CLAUDE.md参照）。

## 全体のアーキテクチャ

```
┌─ フロントエンド（TypeScript） ──────────┐
│ React + Vite                             │
│  ├ 盤の描画: Pixi.js                     │
│  └ 境界の検証: Zod                       │
└──────────────┬───────────────────────────┘
               │ HTTP・JSON（Phase1はREST。Phase2でSSEを加える）
┌──────────────┴─ バックエンド（Python） ──┐
│ APIの層: FastAPI                         │
│  ├ API用の型（Pydantic）と変換           │
│  └ 入力をどのMoverに届けるかの判定       │
│      ↓（依存は内側へ）                   │
│ ドメイン                                 │
│  ├ GameSession（run()ループ）・Mover     │
│  ├ ルールのモジュール（合法手の判定）    │
│  └ 盤・駒・着手                          │
└──────────────────────────────────────────┘
  Phase2: USIエンジン（別プロセス）  Phase3: PostgreSQL
  Phase5: Unityクライアント（同じAPIを使う別のクライアント）
```

- **ルールと状態の真実の源は、常にバックエンド**。フロントエンドは、サーバーが配信する状態を描画し、ユーザーの意図を送るだけの薄いクライアントに徹し、ルールのロジックを持たない。将来のUnityクライアントを、同じAPIを使う別のクライアントとして足せるようにするため
- **境界では両側で検証する**。バックエンドはPydantic、フロントエンドはZodで、受け取ったJSONを境界でパースする。型を共有して境界そのものをなくす構成（tRPC等）は採らない
- **APIの契約の持ち主はAPIの層**。ドメインはAPIの層を知らない（[`api.md`](api.md)「API用の型と変換」）
- バックエンドはDockerで動かす
- 各層の詳細は、ドメインは[`domain.md`](domain.md)、API契約は[`api.md`](api.md)、フロントエンドは[`frontend.md`](frontend.md)。全体を貫く設計方針は下記「内部の仕組みとクライアントへの届け方を分ける」

## Walking Skeletonの要件

Phase1の最初の到達点。「駒が動いて、取り合いすら起きない序盤だけなら指せる」ことを目指す。

- 平手の初期配置の盤面がある
- 駒は、その駒の動きに沿って、他の駒がいなければ移動できる
  - 飛車・角・香車は、通り道と移動先の両方が空いている必要がある。それ以外の駒は移動先だけ。桂馬は途中の駒を飛び越えられる
  - 移動先に相手の駒がいる場合も移動できない（駒取りはない）
  - 成り・行き所のない駒の判定もない。桂馬が敵陣の奥に入ると動けなくなることがあるが、許容する
- 人間の手番と相手（Bot）の手番を処理できる。相手は`RandomMover`（合法な移動からランダムに選ぶ）
- 新規対局を始められる（リセットの操作は作らない。[`api.md`](api.md)「新規対局とリセット」）
- 終局はない。駒を取れない以上、ゲームの中で終局が起こりえないため。終局がない前提の実装を作らず、終局の仕組みごとPhase2に留保する

## 内部の仕組みとクライアントへの届け方を分ける

- **内部**: `run()`ループが、今の手番のMoverの`propose_move()`を待つ。人間の手もBotの手も同じ形で待つ。**GameSession以下は人間とBotを区別しない**（`if is_human:`のような分岐を入れない）。外部からの入力をどのMoverに届けるかを判定するのは、APIの層だけ
- **クライアントへの届け方**: Phase1では、POSTのレスポンスを、Botが応答して再び人間の手番に戻るまで待たせてから返す（同期）。Phase2の序盤でSSEによる非同期の配信に切り替える。切り替えで変わるのは届け方だけで、内部には手を入れない
- 届け方の問題を内部の分岐で解決すると、後で清算に手こずるため、この2つを最初から分けておく

詳しい経緯: [`rationale/overview.md`](rationale/overview.md)「内部の仕組みとクライアントへの届け方を分ける」

## 開発基盤

Phase1で入れる。

- Docker化（バックエンド）
- pytest・Vitest・Zod
- ruff（Pythonのリンター・フォーマッター）、pyright（Pythonの型チェッカー）
- ESLint + Prettier（フロントエンドのリンター・フォーマッター）
- GitHub ActionsによるCI
- import-linter（Pythonのパッケージ間の`import`の向きを検査する）。ドメインがAPIの層を`import`しないこと（[`api.md`](api.md)「API用の型と変換」）をCIで守らせる

型チェッカーはpyright。Pydanticを設計の中心に置くため、Pydanticへの対応の実績を重視した（pyrightはプラグインなしで対応している）。

詳しい理由と外した案: [`rationale/overview.md`](rationale/overview.md)「開発基盤」

## ポート

| 用途 | ポート |
|---|---|
| フロントエンド（Viteの開発サーバー） | `5173` |
| バックエンド（FastAPI） | `8000` |

- 既定の番号をこのプロジェクトが独占する（並走する他のプロジェクトは別の番号へ逃がしてある）
- **使用中なら別のポートへ逃げずに、起動を失敗させる**。逃げると、どのポートで動いているかを追えなくなり、並走する他のプロジェクトのポートを奪うことにもなるため
  - Vite: `server.port`に加えて`server.strictPort: true`を設定する（`port`だけでは、使用中のとき次の番号へ黙って逃げる）。`vite preview`にも`preview.port`・`preview.strictPort`を設定する
  - `docker compose`: ホスト側の番号を必ず書く（`"127.0.0.1:8000:8000"`）。コンテナ側だけを書くと、ホスト側にランダムな番号が割り当てられる。ホスト側を`127.0.0.1`に限定し、同じネットワークの他の端末に開発用のサーバーを晒さない
- 番号を1か所（`.env`等）に書いて各所から読むか、フロントエンドからバックエンドへの接続をViteのプロキシにするかCORSにするかは、Walking SkeletonのIssueで決める

## 画面

Phase1の画面。

- 盤面はPixi.jsで描く。Reactの画面の中にPixi.jsの描画面を置き、盤以外のUI（ボタン等）はReactで作る。盤をReactのDOM（HTML要素）で組んでから後でPixi.jsへ移行すると煩雑なので、最初からPixi.jsにする
- Walking Skeletonの駒は漢字の文字で描く。Phase1の最後で画像に切り替える

フロントエンドの技術と構造は[`frontend.md`](frontend.md)。詳しい経緯: [`rationale/overview.md`](rationale/overview.md)「画面」

## 後のPhaseのために今から守る前提

- **後手を選べるようになる前提で設計する**。盤面の表示の向きや座標の扱いを、人間が先手であることに依存させない
- **「人間は1人だけ」という前提の実装を置かない**。置く場合も、清算できる負債（`debt`のIssueと「暫定実装」の注記付き）にする
- **駒落ち・持将棋は、後から組み込める余地だけを残す**。実装はしない
- **棋譜は内部で構造化して持ち**、将棋の表記の文字列や棋譜ファイル（KIF・CSA等）へ変換できるようにする
- **局面の文字列表現にはSFENを使う**。盤面注入の入力形式にSFENを使えば、棋譜の読み込み・USIエンジンとの受け渡しにも同じ仕組みを使い回せる

## ロードマップ

| Phase | 内容 |
|---|---|
| 1 | Walking Skeleton（上記）、開発基盤、駒の画像化（Phase1の最後） |
| 2 | 非同期化（SSE、序盤）、駒取り・成り・打ち（早期）、盤面注入（早期。検証のため）、王手判定・終局、反則処理、持ち時間、USIエンジン（やねうら王等。Phase2の山）と評価値・読み筋の表示、待った（USIエンジンの直後。意味のある対局ができるようになってから） |
| 3 | 棋譜のファイル書き出し（KIF・CSA等）、ローカルでのPostgreSQL構築（Cloud SQLを見越す）、着手のリクエストでの手数による確認（最後。Phase4の同時の操作に備える。[`api.md`](api.md)「エラー」） |
| 4 | 認証（Firebase等）、人間同士の対局・観戦、デプロイ（Cloud Run・Cloud SQL等。最初のデプロイの前に、クライアントのレスポンスの検証をTolerant Readerへ切り替える。[`api.md`](api.md)「レスポンスへのフィールド追加と後方互換性」） |
| 5 | Unityクライアント |

- 後手を選べるようにする
- 「すべてのMoverがHTTPの境界を越える」抽象化（後のPhase。Phase1の形は妥協ではないので`enhancement`）
- 駒落ち・持将棋（後の方）
- 画面の演出
- 非機能面の作り込み
- 設計書の外した案・経緯（`rationale/`）をADR（Architecture Decision Records）の形式に整備する（Walking Skeletonの後）
