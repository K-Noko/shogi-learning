# 設計書: API契約

Walking Skeleton（Phase1）の分だけを書く。設計書の読み方は[`overview.md`](overview.md)を参照。外した案・経緯・長い論証は[`rationale/api.md`](rationale/api.md)に、同じ見出しで置く。

## 対局の作成とURL

- 対局は`POST /games`で作成し、サーバーが振った対局ID（UUID）を返す。以降の操作は`/games/{id}/...`で行う
- IDをURLに入れないと、「サーバーに対局は1つしかない」という前提が契約に入り、全クライアントを同時に変えないと直せない負債になる
- IDはサーバーが振る。クライアントに振らせると、IDを振る責務がクライアントに漏れる

外した案: [`rationale/api.md`](rationale/api.md)「対局の作成とURL」

## 新規対局とリセット

- Phase1に「リセット」の操作は作らない。やり直したいときは、`POST /games`で新しい対局を作る。UI上の名前も「新規対局」とする
- 「リセット」という名前は、「この対局の持ち物（設定・ID等）を残したまま、盤面だけ初期局面に巻き戻す」操作のために取っておく。これは全手の「待った」と同じなので、必要になったらPhase2の「待った」の仕組みの上に作る
- 新しい対局を作れば、何も持ち越さないのが既定になる。持ち越したいもの（今後の設定値等）は、`POST /games`のリクエストに明示的に書く
- クライアント側は、対局の状態を対局IDに紐づけ、IDが変わったら作り直す（Reactなら`key={gameId}`等）。前の対局の表示状態（直前の手の強調、選択中の駒等）を持ち越さないため
- プレイヤー単位の設定（表示の好み等）は対局とは寿命が違うので、対局に持たせない。置き場所は認証（Phase4）で決める
- **古い対局の片付けはPhase1では行わない（`debt`）**。古い対局はメモリに残り、その`run()`ループは人間の手を待ったまま止まるが、人の操作でしか増えず、止まって待っているだけなのでPhase1では実害がない。回収するときは、一定時間アクセスのない対局をサーバー側で止めて捨てる形にする

詳しい理由と経緯: [`rationale/api.md`](rationale/api.md)「新規対局とリセット」

## 盤面のレスポンス

- 盤面は構造化したマス目で返す。各マスは駒（種類・持ち主）か、空（`null`）
- マス目の配列はワールド座標（[`domain.md`](domain.md)「座標」）の順で返す。`board[y][x]`で、`board[0][0]`が9筋一段。人間がどちらの手番を持っているかに依存させない。盤を反転して表示するかどうか（カメラ座標への変換）はクライアントが決める
- 駒の種類と持ち主は英語で表す（[`domain.md`](domain.md)「用語」）。漢字の表記はサーバーから返さず、クライアントが種類・持ち主（Phase2からは成りも）の組み合わせから決める。表示のための変換であり、ルールのロジックには当たらない
- 持ち駒と、駒が成っているかどうかは、Phase1のレスポンスに含めない。Phase1では常に空・常に`false`なので、駒取り・成りを入れるPhase2で足す。契約に載せたフィールドは「この値は変わりうる」という約束になるので、変わらないことをサーバーが知っている値は載せない
- **Phase1では、バックエンドの外にSFENは出さない**。クライアントがSFENを必要とする場面がPhase1にはないため。クライアントにSFENが要るようになったら（局面のコピー機能等）、サーバーがレスポンスに`sfen`のフィールドを足す。クライアントで構造化したマス目からSFENへ変換しない（表記のロジックがフロントエンドに漏れ、Unityクライアントにも重複するため）

詳しい理由と外した案: [`rationale/api.md`](rationale/api.md)「盤面のレスポンス」

## Phase1のエンドポイント

| メソッド | パス | 内容 |
|---|---|---|
| `POST` | `/games` | 対局を作成し、`201`で対局IDと状態を返す |
| `GET` | `/games/{id}` | 今の状態を返す |
| `POST` | `/games/{id}/moves` | 人間の着手を受け付ける。Botが応答して人間の手番に戻るまで待ってから、そのときの状態を返す（同期） |

- 状態には、盤面（上記「盤面のレスポンス」）、手番、直前の着手、今の局面の合法手の一覧（下記「駒の選択と合法手」）を含める。直前の着手がないと、Botがどこを動かしたかが画面でわからない。履歴全体（棋譜）は、棋譜の表示を作るときに足す
- 対局IDは画面のURLにも入れ（フロントエンドのルーティング）、再読み込みしたら`GET`で同じ対局に戻る

詳しい理由と外した案: [`rationale/api.md`](rationale/api.md)「Phase1のエンドポイント」

## API用の型と変換

- **APIの契約（クライアントが依存する形）の持ち主はAPIの層である**。リクエスト・レスポンスの型はAPIの層で定義し、ドメインの型との変換もAPIの層に置く
- ドメインはAPIの層を知らない。ドメインの型をそのままレスポンスに使わず、ドメインの型に`to_api()`のような変換を持たせない。import-linterでCIに守らせる（[`overview.md`](overview.md)「開発基盤」）
- ある時点でAPIの型とドメインの型の中身が同じでも、それは偶然の一致であり、契約をドメインの型に決めさせない。着手もPhase1から着手のAPI用の型を持つ

詳しい理由: [`rationale/api.md`](rationale/api.md)「API用の型と変換」

## 着手の形

- リクエストの着手、レスポンスの直前の着手、合法手の一覧の要素は、すべて同じ着手のAPI用の型を使う。クライアントは合法手の一覧から選んだ手を、そのまま送り返せる
- 座標はワールド座標のオブジェクト（例: 7七は`{"x": 2, "y": 6}`）で表す。盤面のレスポンスの配列と同じ座標なので、クライアントは合法手と盤のマスを変換なしで突き合わせられる。Zod・Pydanticで範囲（0〜8）まで検証できる
- 人間が読むための表記（▲7六歩等）が要るようになったら、サーバーが返す（棋譜の表示を作るとき）
- **Phase1の着手は移動元と移動先だけを持つ**。移動と打つを区別するフィールド（`type`）と、成るかどうかのフィールド（`promote`）は、成り・打つの仕組みごとPhase2で足す。今から持たせると、Phase1で使わないものにPhase1での意味（`promote: true`が来たらどうするか、そのテスト）を与える必要が生まれるため
- リクエストの知らないフィールドは、サーバーで弾く（Pydanticの`extra="forbid"`）。クライアント側の綴り間違いを検知できる

詳しい理由と外した案: [`rationale/api.md`](rationale/api.md)「着手の形」

## エラー

| 状況 | ステータスコード |
|---|---|
| 存在しない対局 | `404` |
| 形が壊れているリクエスト | `422`（FastAPIの既定） |
| 形は正しいが、今の局面では指せない手 | `422` |
| 人間の手番ではない | `409` |

- 指せない手は一律に`422`とする。状態が古い（別のタブで局面が進んだ）のか、クライアントのバグなのかを、サーバーは受け取った手だけからは区別できないため
- 区別が必要になったら、リクエストに「何手目の局面を見て指したか」（手数等の局面のバージョン）を含める（楽観的な同時実行制御）。手数が今と違えば`409`、合っていて指せなければ`422`を返す。古いタブから送った手が、進んだ局面でもたまたま合法だったために意図せず指されることも防ぐ
- 手数による確認は、Phase3の最後（人間同士の対局・観戦が入るPhase4の前）に入れる

詳しい理由: [`rationale/api.md`](rationale/api.md)「エラー」

## 駒の選択と合法手

- 駒を持ち上げる（選択する）操作は画面上の状態であり、対局の状態ではない。サーバーは選択を知らず、最終的な着手だけを受け取る。選択をサーバーの状態にすると、Botには存在しない「持ち上げ」のステップが人間にだけ生まれる（`is_human`の分岐と同じ形になる）
- **状態のレスポンスに、今の局面の合法手の一覧を含める**。クライアントは、その中から移動元が一致する手を探すだけで、持ち上げられる駒と移動先の強調表示を決める。「自分の駒しか持ち上げられない」のような判定も含めて、フロントエンドにルールを残さない
- フロントエンドでの選択の制限は、あくまで表示の都合である。バックエンドは、届いた着手を必ず合法手の判定に通す（[`domain.md`](domain.md)「合法手の判定の置き場所」）
- 合法手を列挙するルールのモジュールは`RandomMover`のために必ず作るので、サーバー側のコストはほぼない

詳しい理由と外した案: [`rationale/api.md`](rationale/api.md)「駒の選択と合法手」

## クライアントに置く変換の線引き

判定の問いは「その知識は、クライアントごとに違ってよいか」。

| 知識 | 置き場所 |
|---|---|
| ルール（何が合法か） | サーバーだけ |
| 表記の約束（筋・段との対応、SFEN、棋譜の文字列、「同」「右」「直」等） | 原則サーバー。正解がドメインで1つに決まり、WebとUnityに別々に実装するとずれるため |
| 描画（カメラ座標への変換、ピクセルの位置、強調の見た目、演出） | クライアント。クライアントごとに違ってよい |

- 例外として、小さく閉じていて変わらない表示のための対応表は、表記の約束でもクライアントに置いてよい（駒の漢字の表記、盤の縁の筋・段の目盛り）
- 表記の約束が、表示のための対応表ではなく処理の途中に入り込むのは避ける。例えば、合法手と盤のマスの突き合わせに筋・段との変換を挟むこと（そのためAPIの座標はワールド座標にした）。クライアントは、`(0, 0)`が9一であることや、`(1, 5)`を「8六」と呼ぶことを知らなくても、描画と着手ができる

詳しい理由: [`rationale/api.md`](rationale/api.md)「クライアントに置く変換の線引き」

## レスポンスへのフィールド追加と後方互換性

- **Phase1〜3は、レスポンスのスキーマをstrict（`z.strictObject`）にし、クライアントを同じ変更の中で追従させる**。サーバーとクライアントは常に同時に変わり、並走する古いクライアントが存在しない。strictなら、サーバー側の綴り間違いや、Zodのスキーマの直し忘れを検知できる
- **Phase4の最初のデプロイの前に、Tolerant Reader（`z.object`の既定のstrip。知らないキーを捨てる）へ切り替える**。デプロイ後は、古いクライアントが新しいサーバーと並走するため。デプロイ後に切り替えても、配られた古いクライアントはstrictのまま残るので、切り替えはデプロイの前提条件である
- 切り替えた後、**後方互換な変更として扱えるのは、古いクライアントが無視しても振る舞いが壊れないフィールドの追加だけ**。次の2つは互換性のない変更として扱う
  - 値の種類の追加: `z.enum`や判別可能なUnionは、知らない値が来るとパースに失敗する
  - 既存の意味を変える追加: パースは通るが振る舞いが壊れる（例: 終局を表すフィールドを足しても、古いクライアントは無視して着手を送り続ける）

詳しい理由: [`rationale/api.md`](rationale/api.md)「レスポンスへのフィールド追加と後方互換性」。一般的な対処の調べものは`docs/references/api-compatibility.md`
