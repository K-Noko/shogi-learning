# 規則の守らせ方の棚卸

CLAUDE.mdの規則を1つずつ、どの仕組みで守らせるかで分類したもの。方針はCLAUDE.mdの「規則の守らせ方」（機械で検査できる規則はCIで守らせる。文章は予防、CIは保証）。「状態」が「決定」のものは合意済み、「候補」のものは、該当するIssueを切り出すときに改めて決める。

## 守らせ方の種類

関所の位置で分ける。1つを選ぶのではなく、重ねて使う。

| 関所の位置 | 手段 | 効く相手 |
|---|---|---|
| 作る仕組み自体 | 型、Issue forms（テンプレートごとのラベルの自動付与・必須項目） | 誰にでも |
| 作る直前 | Claude CodeのHook | Claudeだけ |
| 作った後 | CI（GitHub Actions）、リンター、テスト | 誰にでも |
| マージの直前 | GitHubのブランチ保護（必須のステータスチェック） | 誰にでも |
| 読まれたとき | 文章（CLAUDE.md・設計書・スキル） | Claude（読まれた場合だけ） |

文章の置き場所は、「誰に見せるか」と「いつ読ませるか」の2つの軸で決める。

| | 常に読まれる | 必要なときだけ読まれる |
|---|---|---|
| 公開 | CLAUDE.md | リポジトリのスキル（コミットする） |
| 非公開 | CLAUDE.local.md | 非公開のスキル |

持ち主の手元の作業場所（gitignore対象）を前提にする規則は、非公開の側に閉じる。

## 規則ごとの分類

### プロジェクトの位置づけ（判断をAIに委ねきらない等）

| 守り方 | 状態 |
|---|---|
| 文章（CLAUDE.md） | 決定 |
| 文脈を持たせたサブエージェントでの監査（例: 提示せずに実装が先行していないか） | 候補。機械の検査ではなく、文脈による監査になる |

### 開発の進め方（負債の記録・留保）

| 規則 | 守り方 | 状態 |
|---|---|---|
| 留保の判断、テストケースの設計を留保しない | 文章 | 決定 |
| `debt`のIssueに発生元のIssue番号を書く | Issue forms（`debt`のテンプレートの必須項目） | 候補 |
| コードの「暫定実装（#Nで解消予定）」 | CIで、`#N`が実在する`debt`のIssueか、閉じたIssueを指す注記が残っていないかを検査する（負債を返したのに注記だけ残る腐り方を捕まえる） | 候補 |

### テスト設計の分担

| 規則 | 守り方 | 状態 |
|---|---|---|
| テストケースはユーザーが指定する、Vitestの型はユーザーが作る | 文章 | 決定 |
| プロパティベーステストを使う箇所 | テストのテスト（ミューテーションテスト等）でCIに載せる余地 | 候補 |
| テストが本当に失敗シナリオを防いでいるか | ミューテーションテスト（Pythonはmutmut、JSはStryker） | 候補 |

### アーキテクチャの前提

| 規則 | 守り方 | 状態 |
|---|---|---|
| ドメインがAPIの層を`import`しない（依存の向き） | import-linter（CI） | 決定（Phase1の開発基盤） |
| ルールと状態の真実の源はバックエンド | フロントエンドのテストで、わざと将棋のルールと矛盾する合法手の一覧を渡し、画面がそのとおりに強調表示するかを検査する。正しい一覧では、フロントエンドが自前でルールを計算していても結果が一致して漏れを検出できないため、「正しさ」ではなく「従順さ」を検査する | 候補 |
| 境界で両側が検証する | typescript-eslintの`no-unsafe-*`系の規則（`response.json()`の`any`をパースせずに使うことを禁止）。バックエンドのテストで書き出したレスポンスの実例を、フロントエンドのテストでZodのstrictなスキーマに通す（型を共有せずに、両側の形の一致を確かめる） | 候補 |
| 形の分岐があるリクエストを型で弾く | pyright、壊れたリクエストに`422`が返ることのテスト | 候補 |

### 規則の守らせ方・設計書とドキュメント

| 守り方 | 状態 |
|---|---|
| 文章（CLAUDE.md）。「機械で検査できるか」の判定自体が意味の問題なので、機械では守れない | 決定 |
| 「機械で検査できるか」の判定を、スキルやサブエージェントに切り出す | 候補 |

### コーディング規約

| 規則 | 守り方 | 状態 |
|---|---|---|
| すべての`def`にdocstringを付ける | ruffのpydocstyleの規則（`D`系）。書き方の規約なので、文章にも残す | 候補 |
| テスト関数のdocstringに保証内容と失敗シナリオを書く | 書式を決めれば（例: 見出しの語）形式だけは検査できる。中身は文章 | 候補 |
| 拡張の余地があるクラスに、引き受けないことを「恒久の境界」か「Phaseの留保」かを明記して書く | 文章。旧文言「今後を見据えた規定」は、本来「今後どう拡張されても変わらない規定」（恒久の境界）の意味だったが、「今後に備えた」とも読めて伝わらなかった。否定の形の規則は「永久に」と「今は」が同じ字面になるので、どちらかを必ず明記する形に書き直した | 決定 |
| 非自明な意図をコメントで残す | 文章 | 決定 |
| 日本語で書く | 文章。検査を作り込む工数に対して、英語で書かれても壊れるものがない | 決定 |

### Git運用・Issue運用・ラベル

| 規則 | 守り方 | 状態 |
|---|---|---|
| PRタイトルの接頭辞 | GitHub Actionsで検査し、ブランチ保護の必須チェックにする＋文章（CLAUDE.md）。PRのタイトルは立った後でも直せ、取り返しがつかなくなるのはマージの瞬間なので、関所はマージの直前で足りる。作る直前のHookは過剰 | 決定 |
| 直接`main`にマージしない | ブランチ保護 | 候補 |
| Issueのラベルは必ず1つ | Issue forms（`enhancement`・`bug`・`debt`のテンプレートがそれぞれラベルを付け、テンプレートなしのIssueを禁止する）。Issueには「マージの直前」の関所がなく、Actionsで赤くできないため、作る仕組みで守る | 候補 |
| Issueの下書きの手順 | 持ち主の手元の作業場所を前提にするので、非公開の文章（CLAUDE.local.md）に置く。手順が固まったら非公開のスキルへ移す | 決定 |

- **注意**: 非公開のリポジトリでは、GitHubの無料プランだとブランチ保護が効かない可能性がある（未確認）。このリポジトリは現在非公開で、公開を予定している。ブランチ保護を設定するときに確かめる

### 開発サーバーのポートの固定

| 守り方 | 状態 |
|---|---|
| 設定の振る舞い。Viteの`strictPort`と、`docker compose`でホスト側の番号を明記することで、使用中なら別のポートへ逃げずに起動が失敗する（`docs/design/overview.md`「ポート」） | 決定 |

### Claudeが実行してよいコマンド

| 守り方 | 状態 |
|---|---|
| 文章（CLAUDE.md） | 決定 |
| Hook。コマンドの禁止リスト（`npm run dev`、`uvicorn`等）は言い換えですり抜けるので、害の仕組み（バックグラウンド実行の子プロセスが生き残る）を狙い、`run_in_background`を使うコマンドを`docker compose`以外すべて拒否する。フォアグラウンドで持続するコマンドがタイムアウトしたときに子プロセスが残るかは未確認で、残るなら禁止リストを補助として足す | 候補 |
